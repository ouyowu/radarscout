# RadarScout B2B analytics plan

Task: `TD-RADARSCOUT-B2B-ANALYTICS-PLAN-0`

## 1. Purpose

This document defines a safe, staged analytics plan for RadarScout's B2B partner pages:

- `/partners`
- `/suppliers`
- `/destination-partners`

The goal is to understand whether the static partner pages create useful inbound interest, without adding backend lead capture, cookies, third-party scripts, CRM, account login, or database writes in this task.

This plan applies only to RadarScout. It does not apply to ThaiEleHub, Shopify theme work, Shopify product content, or Shopify checkout behavior.

## 2. Current state

Current B2B model:

- static pages
- conservative `noindex,nofollow`
- email-first intake through `mailto:hello@radarscout.io`
- manual partner lead triage
- no backend form
- no database writes
- no CRM
- no account, portal, or dashboard

Related documents:

- `docs/radarscout-partner-conversion-next-steps.md`
- `docs/radarscout-partner-lead-triage-playbook.md`

Current production gate:

- Partner mailto prefill is merged and preview-passed.
- Production deploy still requires explicit approval for merge SHA `592204a0d1289cb0506cc24bad589e2d68449335`.

## 3. Measurement questions

RadarScout should answer these questions before adding a backend intake form:

1. Are B2B pages being visited?
2. Which B2B page gets the most interest?
3. Do visitors click the email CTA?
4. Which source page produces the most useful partner inquiries?
5. Are inquiries mostly travel partners, suppliers, or destination partners?
6. Are current page expectations clear enough to reduce out-of-scope emails?
7. Does `mailto:` remain sufficient, or is a structured form needed later?

## 4. Metrics to track later

### Page-level metrics

Recommended future metrics:

- page views for `/partners`
- page views for `/suppliers`
- page views for `/destination-partners`
- unique visitors by page
- referrer category when available
- device category
- country or region only if privacy-safe and aggregate

Do not collect:

- precise location
- personal identity
- contact details
- cross-site behavioral profiles
- sensitive traveler data

### CTA-level metrics

Recommended future metrics:

- click count on partner CTA
- click count on supplier CTA
- click count on destination-partner CTA
- click-through rate by page
- device category for CTA clicks
- source page label

Do not collect:

- email body contents
- email recipient identity beyond the public `hello@radarscout.io`
- private supplier data
- traveler names
- booking references
- payment details

### Manual inbox metrics

These can be tracked manually in a spreadsheet before adding software:

- received date
- source page label
- lead category
- A/B/C/D fit score
- destination focus
- public website or product link present
- booking partner link present
- response sent
- call requested
- outcome notes

Manual notes should avoid storing sensitive traveler or payment information.

## 5. Recommended analytics phases

### Phase 0: Manual email tracking

Start with manual tracking only.

Recommended artifact:

- local or private spreadsheet managed by the human operator

Columns:

- date received
- source label
- lead type
- destination focus
- fit score
- public link present
- booking link present
- response template used
- follow-up status
- notes

No repo changes are required.

### Phase 1: Privacy-safe page analytics plan

Create a separate implementation plan comparing privacy-safe analytics options.

Candidate approaches:

- Vercel Web Analytics
- Plausible
- Simple server log review
- no analytics until real partner outreach begins

Decision criteria:

- privacy posture
- cookie requirements
- implementation complexity
- visibility into page views
- visibility into CTA clicks
- operational overhead

Do not implement tracking until a separate approval exists.

### Phase 2: Static CTA event instrumentation

If approved later, instrument only static B2B CTA clicks.

Allowed future event names:

- `b2b_partner_mailto_click`
- `b2b_supplier_mailto_click`
- `b2b_destination_partner_mailto_click`

Allowed properties:

- page path
- source label
- CTA label
- environment
- timestamp generated by analytics tool

Forbidden properties:

- email body
- email address typed by the sender
- traveler name
- booking reference
- product private data
- supplier private rate
- payment details
- checkout details

### Phase 3: Structured intake decision

Only after enough real emails arrive, decide whether `mailto:` should remain or whether a future form is warranted.

If a form is considered, create a separate design document first.

The form decision must answer:

- what fields are necessary
- whether any data is personal data
- where data would be stored
- who can access it
- deletion process
- spam prevention approach
- whether a database schema is required
- whether email-only remains safer

Do not add a form, API route, database model, or schema in an analytics task.

## 6. Privacy and compliance guardrails

Keep analytics minimal.

Do not collect:

- payment information
- checkout data
- booking submissions
- passport or ID data
- traveler personal details
- precise location
- supplier private rates
- Bókun backend data
- Bókun login or credentials
- inventory data
- live availability data

Do not add:

- third-party script without explicit approval
- cookie-based tracking without a cookie policy review
- database writes without explicit approval
- CRM integration without explicit approval
- tracking pixels in email templates
- cross-site retargeting

## 7. SEO boundary

B2B pages currently remain `noindex,nofollow`.

Analytics planning must not change:

- robots metadata
- sitemap membership
- homepage/nav links
- SEO index/follow state

Any future indexing decision for B2B pages requires a separate SEO readiness task.

## 8. Implementation guardrails for future tasks

Any future analytics implementation must explicitly confirm:

- no production deploy without approval
- no `index,follow` opening
- no sitemap changes unless scoped
- no Bókun API calls
- no checkout, payment, cart, or booking submission
- no live availability or inventory behavior
- no DB/schema/env changes unless approved
- no login, account, portal, CRM, or supplier dashboard unless separately scoped
- ThaiEleHub and Shopify remain untouched
